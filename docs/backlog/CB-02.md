# CB-02 — REST credential protection

Sprinter: `7fb42679e087`. Associated GitHub issue: none.

This branch enforces access versus refresh token types, complete numeric token
claims, and current credential subjects on every authenticated request. API key
rotation therefore revokes existing access and refresh tokens immediately.
Credential retrieval and rotation require loopback plus an existing API key or
access token. First-time owners obtain the key from the owner-readable `api.key`
file or local daemon IPC; HTTP loopback is no longer a bootstrap credential.
Credential files use mode `0600`, including pre-existing files. CORS is closed
by default. Tests exercise these boundaries using isolated state and Fastify
injection, without a live daemon or provider.

The credential serialization audit now excludes remote API keys from host
listings, creation responses and health snapshots, removes legacy URL credentials
and known credential values from public error metadata, and rejects new host URLs
containing userinfo/query credentials. Orchestration and Telegram/provider state
files use mode `0600` on creation and reload. An explicit `allowedOrigins` server
option accepts only complete HTTP(S) origins; matching is exact, credentials are
not ambient, and authentication remains required. Request logging redacts API
keys, bot tokens, signing secrets, authorization and request URLs.

Local source acceptance is covered by isolated tests for host serialization,
file permissions, exact-origin preflight, denied origins and authenticated-route
protection. The separately deployed dashboard and credential handover remain
operator acceptance gates; no production configuration or service was changed.
