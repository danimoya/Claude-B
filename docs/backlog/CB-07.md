# CB-07 — remote submission deadlines and completion contract

Sprinter: `aca62e809f0f`. No matching GitHub issue was open on 2026-11-07.

The scoped fix places authentication, optional token refresh, fallback
reauthentication, operation submission, and response-body consumption under one
request deadline. A failed refresh cannot start a fresh authentication request
after that deadline. Every fetch receives the same AbortSignal, all exit paths
clear the timer, and failures before authentication completes now affect host
health accounting. Configured health-check timeouts also cover authentication.

The client does not retry a submitted mutating POST. If a prompt response times
out after submission, execution may already have started on the remote host;
the existing error result is uncertain, and callers must not resubmit it blindly.
Controlled loopback tests cover stalled authentication headers/body, stalled
refresh, fallback authentication, incomplete operation bodies, health-check
budgets, timer cleanup, and one submission after a response timeout. Tests use
no actual remote service, agent or provider account.

CB-07 remains partial. The server currently acknowledges prompt submission as
`queued`, while the synchronous client recognizes only `completed`; a successful
submission therefore is not proof of completion. Completing the blueprint
requires these separately reviewable steps:

1. Add an explicit `accepted` receipt with a stable task ID and durable state on
   the receiving host; preserve the distinction from completed output.
2. Expose task-specific status/result polling with terminal success, failure and
   cancellation records. Bound polling and response transfer by a shared caller
   deadline, and retain the receipt when that deadline expires.
3. Add idempotency keys and an uncertainty type before enabling mutation retry
   or host failover. Reconcile existing receipts after reconnect/restart instead
   of replaying ambiguous POSTs.
4. Propagate host enable/disable changes to routing immediately and document
   failure classification across the orchestration manager, CLI and REST API.
5. Test accepted-versus-completed behavior, disconnections before/after receipt,
   restart reconciliation, cancellation and duplicate submissions with isolated
   two-host fixtures before any operator-managed rollout.

No deployed host, credentials, daemon, polling owner or remote task was changed.
