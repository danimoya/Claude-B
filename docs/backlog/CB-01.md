# CB-01 — shared state, startup ownership and project targeting

Sprinter: `c701558e08ce`. GitHub issue: none linked.

The IPC client, CLI launcher and daemon resolve the same absolute `CB_DATA_DIR`,
including relative and `~/` paths. Startup uses the package-relative daemon entry
and current Node executable. Concurrent clients share one connection; request
timers are cleared/unreferenced, and disconnect/close promptly rejects pending
requests instead of stranding them.

Daemon ownership uses an exclusive filesystem claim, strict complete PID parsing,
serialized stale-lock recovery, live-process and active-socket checks, and inode
identity for cleanup. Malformed/unreadable/foreign ownership fails closed. State,
PID/lock and IPC socket permissions restrict access to the owning user. Cleanup
never removes another owner's replacement files or active socket. Startup errors
release only this candidate's ownership.

CLI session creation, normal prompts and fire-and-forget send the caller's
working directory. Implicit selection reuses only a session in that canonical
project; concurrent first submissions create one project session. Explicit
`--select` targeting remains explicit and preserves the target's working directory.
Watching binds to the returned session ID rather than another caller's global
selection. Startup readiness uses the actual `daemon.status` IPC method and
closes every probe client.

Isolated Unix-socket, filesystem ownership/race and project-selection tests cover
these contracts. Native daemon integration runs use disposable state and fake
Claude, never the executing installation. No live state or daemon was changed.

CI additionally exercised immediate filesystem inode reuse during ownership
cleanup. The lock now retains an open descriptor and verifies the recorded PID
before recording its socket or deleting state; replacement and in-place owner
changes are preserved. Deterministic regressions cover both cases.
