# CB-08 — Chat ownership and usable voice edits

Sprinter: `7af5602fb409`.
GitHub issue: none linked in the retrieved blueprint item.

Notification-to-session, TTS result and pending voice
prompt maps use both chat and message ID. Confirmations in different chats no
longer overwrite or block each other when Telegram reuses a message ID. Outgoing
notifications require a paired positive private-chat ID and honor the current
allow-list; historical group IDs and newly excluded chats receive nothing.

Bare message IDs saved by older versions have no reliable chat owner and are
dropped on load. Replies and Listen buttons on those old notifications are no
longer available. Select a session and send a new message, or use a newly sent
notification. An explicit reply with a missing mapping is rejected instead of
falling through to a different selected session.

Voice edits update the original confirmation message and preserve its ID.
Failed updates keep edit mode active and leave the prior prompt unchanged;
confirmation waits until a successful edit or cancellation. `/cancel` exits edit
mode without sending a prompt. All routing regressions use temporary config
and a fake Telegram/voice transport; no external message or provider call occurs.

Conversation state now uses a versioned, validated schema and serialized atomic
owner-only replacements. Session selections, edit state, pending confirmations,
notification mappings and playback text survive restart. A voice confirmation
flushes `submitting` plus a stable idempotency key before invoking the submission
callback. Returned durable task receipts are flushed before pending removal.
Interrupted or ambiguous submissions become `uncertain`; repeated confirmation
looks up a known receipt where supported and never resubmits uncertain work.
Storage failure before durable intent prevents the callback entirely. Unknown,
ambiguous and stale session selection callbacks are rejected.

`utils/transcript.ts` parses Claude JSONL, Codex event/response envelopes and
OpenCode session-message exports. It reads a bounded regular-file tail with ESM
imports, includes only visible user/assistant text, and excludes tool results,
reasoning and synthetic context. Dedicated offline format fixtures cover all
three agents.

The native registry resolves an authenticated event or discovered agent to a
canonical `tmux:%pane@foregroundPid-generation` ID. It records the pane PID and
command plus the foreground process start time, persists owner-only validated
state, and restores only that same invocation. Dead, replaced, expired or
unverifiable targets are removed or rejected; an old reply cannot select the
new process occupying its former alias. Native delivery checks identity before
buffering, paste and Enter, passes literal text through stdin and cleans its
private buffer on success or failure. Multiline input preserves LF bytes.

Source acceptance tests cover restart edit recovery, durable intent/receipt
ordering, uncertainty reconciliation, blocked replay, schema corruption,
concurrent atomic writes, scoped chat ownership, transcript formats, dead/reused
panes and agent exit between paste and Enter. Telegram/provider transports are
fake and state is disposable. Native tests also exercise a real Linux tmux
server with a unique private socket, including multiline paste and process
replacement; they never use the default tmux server. Linux/macOS process-format
fixtures supplement these checks, but they do not establish real macOS or
installed native-agent acceptance.

Remaining external acceptance gates are concrete: a dedicated authorized bot
with one polling owner for end-to-end message/voice verification; provider test
accounts and entitlements (including Speechmatics TTS), explicit retention and
charge approval; and real Claude/Codex/OpenCode tmux sessions on Linux and macOS
to validate installed native versions and paste timing, including a real macOS
runner beyond the modeled process fixtures. A process can exit
between the last identity check and a tmux effect; delivery therefore fails
closed on detected changes and never retries an ambiguous native submission.
No production configuration, poller, provider account or service was changed.

The installed standalone OpenCode plugin now forwards up to three visible user
and three assistant turns as bounded `contextTurns`, excluding tool, reasoning,
synthetic and known wrapper text. The authenticated localhost notify route
validates six turns / 600 characters per turn and sends them to the optional
context callback only after canonical pane normalization. This connects native
OpenCode history to voice context without requiring a transcript file path.
A plugin integration test uses mocked native client messages, tmux and fetch;
no OpenCode session or external provider is contacted.
